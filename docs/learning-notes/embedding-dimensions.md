# Embedding 维度与 Matryoshka 表示学习

> 核心认知：**embedding 模型"能出多高维度"是它的能力上限，不代表你要用满**。Matryoshka（俄罗斯套娃）表示学习让同一个模型可以按需输出不同维度，低维截取几乎不损失精度——这正是「支持 2560 维却只用 1024」的底气。

---

## 一、先厘清三个容易混的「维度」

| 概念 | 含义 | 谁决定 |
|------|------|--------|
| 模型能力上限 | 模型训练时的满配维度（如 2560） | 模型本身，改不了 |
| 默认输出维度 | 不传 `dimensions` 参数时 API 返回的维度（qwen3.7 = 1024） | API 约定 |
| 实际锁定维度 | 我们写进 `vector(N)` 列、所有文档统一用的那个 N | **我们主动选** |

最容易混淆的是「能力上限」和「实际用」——支持 2560 不代表要用满。1024 是 API 的**默认输出**，不是模型的上限；我们「锁 1024」是主动选择，不是被模型逼的。

## 二、Matryoshka：为什么低维不亏

Matryoshka 这个词本身就是比喻（俄罗斯套娃）。它的关键特性：

> 向量的维度是**嵌套**的——前 512 维已经装下了语义的绝大部分，越往后每一维的边际信息量越小。

打个比方：一张 2560 像素宽的图缩到 1024 像素基本看不出差别，缩到 512 才略有损失。向量同理——「截取」低维 = 取内层套娃，丢掉的是几乎无用的尾部维度。

## 三、本项目为什么锁 1024（三个约束）

| 约束 | 说明 |
|------|------|
| Neon 免费版硬上限 | pgvector 索引维度上限 1536，选 2560/3072 直接超限 |
| 存储 + 速度 | 维度越高，每行 float 越多、算距离越慢。几百 chunk 1024 绰绰有余 |
| 精度够用 | 中文技术文档检索 1024 维召回已足够，再高是浪费 |

（决策依据见 [RAG 设计文档决策 2](../dev-log/2026-08-19-rag-knowledge-base-design.md)）

## 四、不可逆铁律

`vector(1024)` 列一旦建好就定死：**改维度 = 重建全库**；且所有文档必须用**同一个模型的同一维度**算向量，混用会让检索静默失效（不报错，只是结果变成噪声）。

## 五、实践落点

写入向量时有两种保证「永远是 1024」的写法：

1. **不传 `dimensions`**，依赖默认值（简单，但默认值漂移时悄悄拿错维度）
2. **显式传 `"dimensions": 1024`**（自文档化，防默认值漂移污染向量列）

倾向第 2 种——一行代码的成本，换一个「维度永远正确」的保证。落在 `embeddings.ts` 实现时敲定。

## 实测记录

- 2026-08-29：Apipost 调 `qwen3.7-text-embedding`，不传 `dimensions`，返回 `data[0].embedding` 数组长度 = **1024** ✅，维度正式锁定。
