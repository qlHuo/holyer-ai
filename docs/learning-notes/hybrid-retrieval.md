# 混合检索：向量检索、全文检索与 RRF

> 核心认知：**向量检索与全文检索是两种互补的召回方式**——向量的盲区（精确术语）恰是全文的强项，全文的盲区（同义改写、语义泛化）恰是向量的强项。混合检索 = 让两者并行召回，再用 **RRF** 融合。RRF 的精髓是**只看名次、不看分数**。

---

## 一、总览：两种召回，不同的"看世界"的方式

检索有两大流派 —— **词面检索（sparse）** 与 **语义检索（dense）**。全文检索属前者（倒排索引 + TF-IDF 系打分，1960s 就有的老技术），向量检索属后者（神经网络 embedding）。两者独立、互补：

| | 向量检索（dense） | 全文检索（sparse / keyword） |
|---|---|---|
| 原理 | 把文本编码成向量，比语义距离 | 按词面命中，词频/位置加权排序 |
| 擅长 | 语义相近、同义改写、模糊意图 | **精确词、代码标识符、专有名词** |
| 盲区 | **精确字符串**（标识符、版本号、错误码） | 同义词、语义泛化、改写 |
| 中文难点 | 一般无（模型已训练） | **必须分词**（PostgreSQL 原生不分中文） |
| 本项目算子 | pgvector `<=>`（余弦距离） | `tsvector` + `ts_rank` |

---

## 二、向量检索：作用与局限

### 作用（擅长什么）

把文本压缩成**语义向量**，用「距离」衡量相关。它能召回想表达同一意思但**用词完全不同**的内容 —— 用户问「为什么不用现成框架」，语料里写「否决自建 Provider 抽象层的替代方案」，向量照样能对上。这是关键词检索做不到的。

### 局限（机制与后果）

Dense embedding 把语义**压缩进固定的 1024 维**。问题出在：像 `drizzle-orm/neon-http`、`useRuntimeConfig`、版本号、错误码这类**精确字符串，语义含量极低** —— 模型倾向把它映射到「最相近的语义邻居」（≈「数据库驱动」「Edge 兼容性」这个概念），于是**丢失了精确 token 的身份**。罕见标识符还可能被切碎成子词，进一步模糊。

**后果**：查「`neon-http` 和 `postgres-js` 的区别」时，语料里同时有：

| 段落 | 内容 | 谁排前面 |
|------|------|---------|
| X | 精确讲 `drizzle-orm/neon-http` 的驱动限制 | 语义上"像"，但精确词对向量贡献低 |
| Y | 泛泛谈"Edge 环境该用哪种数据库驱动" | **向量可能把 Y 排在 X 前** |
| — | 全文检索则会因**精确命中 `neon-http`** 把 X 顶上去 | 全文的胜场 |

### 一个诚实判断：弊端真实存在，但未必已被评测暴露

这是 **dense retrieval 的结构性通病**，不是本项目特有 -> 业界因此才把 hybrid retrieval 当标配。

但要区分两件事：

- **弊端本身**：真实、结构性，确定存在。
- **是否已造成损失**：取决于**评测集有没有往这个方向出题**。本项目阶段 A 的 12 题偏「概念理解类」，恰是向量的强项，**没探测到**不代表不存在 —— 只是出题方向不同。而本项目语料是**开发文档**，天然含大量代码标识符，精确词查询迟早出现（多半来自开发者本人），且弊端**随语料规模放大**。

> 结论：混合检索既是**补短板**，也是**防患于未然** —— 补的是一个**已存在、只是尚未被现有评测测到**的短板。

## 三、全文检索：作用与局限

### 作用

按**词面**命中，对精确术语、代码标识符、专有名词、错误码"一查一个准"。这类查询里，用户要的就是**那个确切的词**，不是它的近义表达 —— 这正是向量的短板。

### 局限

- **不懂同义词**：查「部署」召不回只写了「上线」的段落。
- **中文必须分词**：PostgreSQL 原生 `to_tsvector` 对中文无效（中文无空格，整句会变成**一个 token**）。而常规分词扩展（`pg_jieba` / `zhparser`）需要 superuser 安装，**Neon 免费层装不了**。

> 解决路子（本项目 3.9 采用）：入库期用 **`Intl.Segmenter('zh', {granularity:'word'})`** 预分词（Edge Runtime 内置、零新依赖），存成空格分隔的文本，再 `to_tsvector('simple', 分词结果)`。查/写两侧用同一分词器，保证落在同一分词空间。

## 四、全文检索的实现机制（与普通 SQL 查询的区别）

### 不是 LIKE，是倒排索引

全文检索**不是**普通数据库查询，而是**数据库内建的检索子系统**。最本质的差别：

| | 普通查询（`WHERE` / `LIKE`） | 全文检索（`tsvector`） |
|---|---|---|
| 匹配方式 | 精确值 / 子串比对 | **词元集合**匹配 |
| 分词 | 无，整串比 | **有**，先解析成词元 |
| **相关性排序** | **没有**（要么匹配要么不匹配） | **有**（`ts_rank` 打分排序） |
| 索引 | `=` 走 B-tree；`LIKE '%x%'` 退化为**全表扫描** | **GIN 倒排索引**，找词很快 |
| 查询能力 | 比较、布尔条件 | 布尔 + **短语邻近**（`<->`）+ 前缀 |

普通 SQL 回答「**哪些行满足条件**」；全文检索回答「**哪些行与这段文字最相关、排个序**」—— 那个**相关性排序**才是"搜"的灵魂。

```sql
-- 普通查询：能找到，但 ① 全表扫描慢 ② 无排序（500 行谁更相关？）③ 同义词搜不到（写「上线」的段子永远不中）
WHERE content LIKE '%部署%'

-- 全文检索：有索引、有排序
WHERE content_tsv @@ to_tsquery('simple', '部署')
ORDER BY ts_rank(content_tsv, query) DESC
```

### 四步实现

1. **文本 → 词元串**：`Intl.Segmenter` 在 **JS 侧**把中文切成词、小写、去停用词、空格连接 → 存入 `content_tokens` 列
2. **词元串 → `tsvector`**：PG 的 `to_tsvector('simple', …)` 只做「小写 + 按空格切 + 记位置」—— 词是**我们切好的** → 由**生成列**自动写入 `content_tsv`
   ```sql
   -- 原料：应用（JS）写入，空格分隔
   ALTER TABLE chunks ADD COLUMN content_tokens text;
   -- 成品：生成列，PG 自动从原料派生（STORED = 物化落盘）
   ALTER TABLE chunks ADD COLUMN content_tsv tsvector
     GENERATED ALWAYS AS (to_tsvector('simple', content_tokens)) STORED;
   CREATE INDEX idx_chunks_content_tsv ON chunks USING GIN (content_tsv);
   ```
3. **查询 → `tsquery`，做集合匹配** —— `@@` 是「是否命中」运算符，本质是**集合相交**，不是算距离
4. **排序 → `ts_rank_cd`**（词频 + 位置 + 权重）

**全程零模型、零 embedding、零外部调用** —— 纯字符串/索引层的事，所以便宜。

### ⚠️ 为什么是「两列」，不能直接 `to_tsvector('simple', content)`

因为 **PostgreSQL 不认识中文**。`content` 是中文原文，`to_tsvector('simple', '推荐1024维')` 会因为中文没空格，把整段当成**一个 token**，查「维」永远命不中。所以必须**先在 JS 侧切词**，再把切好的串交给 PG 建索引。

于是有了「**原料 + 成品**」两列：

| 列 | 谁写 | 作用 |
|---|---|---|
| `content_tokens` | **应用**（`tokenizer.toIndexedText`） | 原料：空格分隔的词元串 |
| `content_tsv` | **PG 生成列**（自动） | 成品：真正的 `tsvector`，配 GIN 索引 |

**关键：检索只碰成品 `content_tsv`；`content_tokens` 只活在「写入 / 回填」阶段。** 两者之间由生成列连起来，应用不需要管 `content_tsv`。

> **生成列**（`GENERATED ALWAYS AS … STORED`，PG 12+）三条性质：① **不能直接写**（INSERT/UPDATE 它会报错）；② 任何改动 `content_tokens` 的操作都会**自动触发重算**；③ 表达式必须 **IMMUTABLE** —— 所以必须写二参的 `to_tsvector('simple', x)`（配置名写死），单参形式依赖会话变量、是 STABLE，**建列会直接报错**。

> 血统注记：PostgreSQL 的 `ts_rank` 近似 TF-IDF 系打分，**不是严格 BM25**（BM25 在 Elasticsearch / ParadeDB 那一档）。个人知识库量级完全够用。

## 五、RRF 算法（Reciprocal Rank Fusion）

### 为什么两路能融合：共用同一批 chunk

算法上两路完全无关，但它们查的是**同一张 `chunks` 表、返回同一个 `chunk_id`** —— 这个公共键让两个排名能对齐：

```
chunks 表（同一批行，两个索引）
┌──────────┬───────────────┬──────────────┐
│ id       │ embedding     │ content_tsv  │
│ (chunk)  │ vector(1024)  │ tsvector     │
└────┬─────┴───────┬───────┴──────┬───────┘
     │      向量索引(HNSW)      GIN 倒排索引
  向量召回 ────┘                  └──── 全文召回
  （比余弦距离）                    （比词面集合命中）
     └──────────┬───────────────────────┘
                ↓ 按 chunk_id 对齐
            RRF 融合 → top-5
```

### 为什么要"融合"而不是"加权求和"

两路召回的输出**不能直接比较或相加**：向量给的是余弦相似度（0~1），全文给的是 `ts_rank`（无固定上界，量纲完全不同）。

传统办法是「各自归一化后加权」，但归一化的上下界**会随每次查询的结果集漂移**，很脆。RRF 绕开了这个问题：**它完全不看分数，只看名次。**

### 公式

```
RRF_score(chunk) = Σ  1 / (k + rank_i)
```

- **`Σ`** = 求和（希腊字母 sigma）—— 对「该 chunk 出现在哪几路」求和
- **`rank_i`** = 该 chunk 在第 i 路列表里的名次（**从 1 开始**）
- **`k`** = 平滑常数，业界默认 **60**
- 没出现的那一路 = 贡献 0（相当于名次无穷大，`1/∞ = 0`）

用 JS 写出来最直观：

```js
let rrfScore = 0
if (chunk 在向量列表中) rrfScore += 1 / (60 + chunk.向量路名次)
if (chunk 在全文列表中) rrfScore += 1 / (60 + chunk.全文路名次)
```

### 关键前提：rank 是相对候选池的

每路先各取 **top-N（如 20）当候选池**，RRF 只在池内排序，最后取 top-K（如 5）。所以 **rank 3 / 20 是前三甲、非常靠前**，"没进榜"（rank > 20）才等于不存在。判断"是否靠前"必须带上列表长度一起看。

### 数字例子（RRF 的哲学）

| chunk | 向量路名次 | 全文路名次 | 计算 | 总分 |
|-------|:--:|:--:|------|:--:|
| **Q**（两路都第 2） | 2 | 2 | `1/62 + 1/62` | **0.032258** ← 胜 |
| P（向量第 1，全文第 15） | 1 | 15 | `1/61 + 1/75` | 0.029726 |
| R（只在向量第 1） | 1 | 未进榜 | `1/61 + 0` | 0.016393 |

**读懂这张表**：

- P 是向量路**第一名**，但全文路只排 15 → 输给 Q
- Q **从没拿过任何一路第一**，但两路都排第 2 → 胜出
- R 单独在向量路第一，只有一路认可 → 垫底

原因：一个 chunk 被**两套原理完全不同**的算法都排到前几名，「真的相关」的概率远高于「只有某一路的爱将」—— 那很可能是那一路的盲区导致的假阳性。

### 为什么是 `1/(k+rank)` 而不是 `1/rank`

| rank | `1/rank` | `1/(60+rank)` |
|:--:|:--:|:--:|
| 1 | 1.000 | 0.01639 |
| 2 | 0.500 | 0.01613 |
| 3 | 0.333 | 0.01587 |
| 15 | 0.067 | 0.01333 |

- `1/rank` 衰减**太猛**：第 1 名是第 2 名的 2 倍 → 单路冠军碾压一切，融合失去意义
- `1/(60+rank)` **平缓**：第 1 名和第 15 名只差 0.003 → 「两路都靠前」能盖过「单路第一」

`k=60` 就是这个**阻尼器**，把名次差距压平到让共识信号主导。数值出自原论文（Cormack et al. 2009），基本不用调。

### 代价

RRF **丢掉了分数的"大小"** —— 一个"几乎完全匹配"和一个"勉强相关"若都是第 1 名，得分一样。换来的是**零校准、跨召回器通用、抗噪**，对两路来源异构（dense vs sparse）的场景明显划算。

## 六、两个常见澄清

### 6.1 Agentic RAG ≠ 更准的单次检索

引入"Agentic RAG（检索做成工具、LLM 决定调用）"时常有一个误解：以为它让检索更准。**不是。** 两者用的是**同一套**向量 top-K：

- **单次检索的精度**：经典 RAG（向量 + 系统提示词）与 Agentic RAG **完全相同**
- **Agentic 改变的是"使用方式"**：何时检索（条件触发）、查几次（可多轮/并行）、拿什么查（LLM 改写 query）、多面问题能否拆解

所以它是**行为层**的收益（更少上下文污染、能处理多跳/追问），代价是**非确定性 + 延迟 + 成本**。要提升"单次检索本身的质量"，得回到检索算法 —— 那就是混合检索（量）+ 重排/Rerank（序）、以及索引增强（见 Contextual Retrieval）。

### 6.2 top-K 不是算法，也不专属于向量

**「top-K」描述的是"取几个"，不是"怎么找"** —— 它是所有检索共同的收尾动作。不管榜单怎么排出来的，最后都要取前 K 个：

| 检索方式 | 排序依据 | 也取 top-K 吗 |
|---|---|:--:|
| 向量检索 | 余弦距离 | ✅ |
| 全文检索 | 词频权重（`ts_rank`） | ✅ |
| 混合检索 | RRF | ✅ |
| Rerank 之后 | 重排模型打分 | ✅ |

两个常被搞混的点：

- **「传统 RAG 用 top-K」→ 说的是朴素 RAG = 向量 top-K**。这句没错，但准确含义是「朴素 RAG **只有向量这一条路**」，**不是「top-K 属于向量」**。
- **历史上 top-K 最早是全文检索的** —— 1960–70 年代 BM25 那一系就已经「相关性排序 → 取前 K」，向量检索反而是后来借了这个词。

**RRF 与 top-K 是正交的两件事**：RRF 解决「怎么把两个榜单合并成一个排序」，top-K 解决「合并完取几个」。本项目 `fuseRRF` 里 `.slice(0, topK)` 就是那个 top-K 动作，但它真正的价值在**前面的 RRF 重排** —— 取前 K 谁都会，难的是决定谁在前。

## 七、坐标系：RAG 检索的三代演进

理解本项目在哪儿，需要这条线：

| 阶段 | 检索层做什么 | top-K 在哪 |
|---|---|---|
| **Naive RAG**（2023） | 向量检索**单路** | 向量榜取前 K |
| **Advanced RAG**（2024） | **混合检索**（向量 + 全文）+ Rerank | 两路各取候选 → 融合 / 重排 → 取前 K |
| **Agentic RAG**（本项目） | 检索成为**工具**，LLM 决定何时查、查几次 | 每次工具调用内部仍是一轮 top-K |

**top-K 三代都没消失**，变的是两件事：**候选从几路来**（1 路 → 2 路 → 2 路 + 重排）、**排序依据**（余弦距离 → RRF 融合 → RRF + 交叉编码器重排）。

本项目的坐标：**检索层 = Advanced RAG**（3.9 混合检索 + RRF；Rerank 未做），**使用方式 = Agentic RAG**（`search_knowledge_base` 工具）。

## 八、本项目落点

阶段 C 的 **3.9 混合检索**：`retriever.ts` 从纯向量拆成 `searchByVector` / `searchByKeyword` / `hybridSearch`（两路各取 top-20 → RRF 融合出 top-5），分词用 `Intl.Segmenter` + 精简停用词表（`server/service/rag/tokenizer.ts`），索引是 `content_tokens` + 生成列 `content_tsv` + GIN。

**实测（2026-09-15，本地，21 题/三模式）**：concept 命中率 hybrid 11/12 与纯向量**持平**（无回退）；**exact 组 MRR 0.926(vector) → 1.000(hybrid)**；仅全文的关键词路 concept 只有 9/12 —— 印证「必须混合、不能替换」。详见 [RAG 阶段 C 实施规划](../dev-log/2026-09-14-rag-stage-c-plan.md) 3.9 节的实测表。
