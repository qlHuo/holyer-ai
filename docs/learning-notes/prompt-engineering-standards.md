# 业界提示词工程落地实践规范

> 规范是「防遗漏」的写作清单，不是「纠错」的测试。它解决「从零写一个完整 prompt 该怎么组织」，不解决「写完怎么知道它对不对」——后者靠评测（见 8-17 评测调优闭环）。

---

## 阅读前提：规范不是万能药

先厘清一个容易踩的认知误区。业界所谓的「prompt 规范」其实混着**三层含义**，各管各的事：

| 层面 | 回答的问题 | 典型产物 | 本项目现状 |
|------|-----------|---------|-----------|
| **① 结构模板框架** | 一个 prompt 该「装哪些内容、按什么顺序组织」 | CO-STAR / CRISPE / 五要素 | 未刻意套用，但 `toolUsageGuidelines` 天然含「任务+约束」 |
| **② 编写方法论** | 怎么写才能让模型表现更好 | Anthropic / OpenAI 官方指南 | 部分落地（工具优先于记忆） |
| **③ 工程化规范** | prompt 作为代码怎么管理、评测、维护 | 模板化 / eval / 版本管理 | 已有 `PromptSegment` 抽象 + 评测脚本 |

**关键前提（承接 8-17 的反思）**：规范是「静态 checklist」，回答「要素全不全」；实测是「动态测试」，回答「行为对不对」。二者作用于不同阶段、不可互相替代。规范的边际价值在 prompt **复杂到一眼看不过来**时才显现（多段约束 / 输出格式 / few-shot / 多工具）；本项目当前 system prompt 只有两段、工具 4 个，规范的收益趋近零——但这不代表规范没用，只说明「现在还用不上」。当工具涨到 6~10 个、prompt 开始堆约束时，下面这些就是唯一防「漏写关键约束」的手段。

---

## 一、结构模板框架（①）

这些框架**本质是同一套要素换名字**，别迷信框架名，掌握核心要素即可。核心永远是：**角色 + 背景 + 任务 + 约束 + 输出格式 + 示例**。

### CO-STAR —— 最常被推荐的全能框架

新加坡 GovTech 提出，适合绝大多数结构化任务：

```
Context   背景：谁在什么场景用，模型需要知道什么上下文
Objective 目标：要完成的具体任务
Style     风格：想要的写作风格（如"技术文档式、简洁"）
Tone      语气：情感基调（如"专业、客观"）
Audience  受众：回答给谁看
Response  输出格式：如"用 markdown 表格返回，三列：…"
```

### CRISPE —— 偏「角色扮演」场景

```
Capacity & Role  能力和角色（你是资深 X 工程师）
Insight          背景洞察（我需要你理解的情况）
Statement        任务陈述（请帮我做什么）
Personality      个性（回答的口吻）
Experiment       示例（给几个期望的输出例子）
```

### 五要素法 —— 国内教程最常用

```
角色 Role        你是一个…
背景 Context     当前情况是…
任务 Task        请完成…
约束 Constraints 要求/限制（不要…必须…）
输出格式 Format  用 JSON/表格/分点返回
```

### ICIO —— 极简版

```
Instruction 指令
Context     上下文
Input       输入
Output      输出
```

> **落地建议**：写任何面向具体任务的 prompt 时，不必背哪个框架，只需保证「角色 + 任务 + 约束 + 输出格式」四要素齐全。框架是 checklist，不是咒语。

## 二、编写方法论（②）—— 大厂官方推崇

### Anthropic 官方原则（与本项目最相关，Agent 跑的是 Claude 兼容格式）

1. **清晰直接** —— 指令放最前面，不要绕弯子
2. **用 XML 标签结构化** —— `<instructions>`、`<example>`、`<output>` 分隔内容，比 Markdown 标题更抗干扰
3. **给 few-shot 示例** —— 示例是比规则更强的约束
4. **让模型先思考再回答** —— 明确要求「先分析，再给结论」（CoT）
5. **角色扮演** —— persona 能显著影响输出质量
6. **工具优先于记忆** —— 能用工具查的，别让它凭记忆编

### OpenAI 官方六大原则

1. 写清晰指令
2. 提供参考文本（RAG）
3. 把复杂任务拆成子任务
4. 给模型思考时间
5. 使用外部工具
6. 系统性测试改动（eval）

### Agent 专属规范（比模板框架更重要）

本项目是 Agent 系统，这一层优先级**高于**上面的模板框架。一个 Agent 的行为质量，分水岭在于「工具描述」写得好不好，而非 system prompt 的模板够不够漂亮：

```
- 明确每个工具的「何时该用」触发条件（场景 → 工具名的显式映射）
- 明确工具输入参数格式（JSON schema + 参数 description）
- 规定工具调用失败时的降级策略
- 规定「能查就不猜」的边界
```

**本项目真实例子**（`server/api/chat/index.post.ts` 的 `toolUsageGuidelines`）：

> 用户明确要求「查询 / 搜索 / 查一下 / 最新」等信息时，应调用 web_search 获取最新结果，不要仅凭记忆回答。

这句话就是「工具优先于记忆」+「场景→工具映射」的落地。它来自 8-17 那次实测调优——原句「不确定就不要调用」太保守，导致边缘场景一律不调工具，改成显式映射后 10/10 通过。**这正说明：方法论（②）里的原则只有落到「场景→行为」的具体约束上才有效，抽象地说「要谨慎」反而有害。**

## 三、工程化规范（③）—— prompt 即代码

Prompt 一旦进生产，就是代码，需要：

| 规范 | 说明 | 本项目现状 |
|------|------|-----------|
| **模板化** | 用变量插值（`{user_name}`），禁止硬编码拼接 | 部分：`PromptSegment` + `buildPrompt()` 拼装 |
| **版本管理** | prompt 存 git，改 prompt = 改代码，走 review | ✅ 已在 git |
| **eval 评测** | 建回归评测集，改 prompt 前后对比 | ✅ `scripts/eval-prompt/`（休眠资产） |
| **分层组织** | system prompt / 工具描述 / few-shot / 用户指令 分离维护 | ⚠️ 分散在 5 层，未集中 |
| **控制长度** | 越长消耗 token 越多、注意力越分散 | 当前很短，无压力 |

> 分层组织这一点，本项目已在 7-09 的 `PromptSegment` 抽象中规划了目标结构（`base.ts` / `react.ts` / `tools.ts` / `skill.ts` / `context.ts`），但 8-17 盘点发现 prompt 实际仍分散在 5 个层级（prompt store、后端拼接、system-prompt 合并、工具描述、结果包装），**规划与落地之间有 gap**——这是后续要补的。

## 四、落地优先级（针对本项目）

按「当前收益 / 实现成本」排序，而不是按业界知名度：

1. **工具调用规范（最优先）** —— 已经在做，继续给每个工具写清「何时该用 + 参数 + 降级」。这是 Agent 质量的分水岭，且是 8-17 实测确认「唯一真问题」所在的层。
2. **system prompt 分层收敛** —— 把分散的 5 层收敛到 `PromptSegment` 抽象（7-09 已设计），让工具描述、结果包装、用户自定义 prompt 各自独立维护。工具涨到 6~10 个时，这是防「改 A 坏 B」的前提。
3. **四要素兜底** —— 写任何新 prompt 时保证「角色+任务+约束+输出格式」齐全，不背框架名。
4. **eval 触发后再扩展** —— 评测脚本保持「休眠」，触发条件是工具数涨 / prompt 开始加 few-shot / 改 A 坏 B 真的发生（已在 8-17 约定）。

## 关键洞察

- **规范分三层，别混用**：模板框架（怎么组织）、方法论（怎么写更好）、工程化规范（怎么管理）。「套 CO-STAR」只是第一层，最不重要的一层。
- **方法论原则要落到「场景→行为」的具体约束才有效**，抽象地说「要谨慎/要专业」反而可能有害（8-17 的「不确定就不调」就是反例）。
- **Agent 项目里，工具描述规范 > system prompt 模板规范**。模板是给「一次性写长 prompt」的场景用的，Agent 的行为质量由工具描述和边界约束决定。
- **规范的适用有边界**：简单 prompt 下边际价值趋近零，复杂 prompt 下是防「漏写关键约束」的唯一手段。判断「什么时候需要规范」比背规范本身更值钱。
