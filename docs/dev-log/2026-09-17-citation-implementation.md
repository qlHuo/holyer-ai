# 2026-09-17 — 引用溯源落地：来源元数据、引用协议与安全边界

> 核心洞察：citation 的前端白名单必须能从 `role:'tool'` 消息里重建 —— 而这份消息文本同时服务「实时流」与「历史回放」，所以把来源元数据缝进它，等于零持久化地同时打通了两条路径。**整条链的支点不在渲染，在工具结果的去向。**

---

## 讨论背景

[3.11 的方案](2026-09-14-rag-stage-c-plan.md)在 2026-09-14 已定稿（数据、渲染、安全、实现流程都写了），本文记录的是**实际落地**：落成什么样、与规划有哪些偏差、安全设计怎么做的、怎么验证的、踩到了什么。

目标回顾：LLM 引用知识库片段时，回答里出现可点击的内联编号，末尾有「参考来源」列表；点击能跳回 GitHub 原文或打开系统内的文档预览并定位到该小节。

两个前置缺口：结构化标题路径在分块阶段就被提取了，却只被拼进切片文本参与向量化、从未落库；GitHub 引入时的仓库路径信息也没随文档存下来。

---

## 实现概览

按数据流分层，每层各管一件事：

| 层 | 做了什么 |
|---|---|
| **数据层** | 切片表新增「结构化标题路径」列（H1→当前节的祖先数组）；文档表新增「原文链接」列。存量数据由回填脚本补齐 |
| **协议层** | 一份前后端共用的来源元数据契约：类型定义 + 构造 + 解析 + 剥离。放在共享目录，避免两边各写一套格式后漂移 |
| **写入侧** | 检索工具在返回结果的最前面输出一行机器可读的元数据块，并给每条片段打一个引用短 key |
| **上下文侧** | Agent 记忆层在「进 LLM 上下文」的唯一闸口处剥离元数据，让它不占 token、也不被模型模仿 |
| **读取侧** | 聊天列表的预览文本、跨对话搜索的结果，在读取边界剥离元数据；历史消息接口**刻意不剥**（前端要靠它重建白名单） |
| **渲染侧** | 渲染前的预处理把白名单内的引用标记换成内部链接；链接渲染规则拦截该 scheme 输出可点击 chip；回答末尾追加来源列表组件；点击无外链的来源时打开预览弹层 |
| **来源链接** | GitHub 引入文档时构造原文 blob 链接一并入库（复用仓库路径改写所用的同一套编码） |

回填脚本值得单独说一句：它**重新分块**来推导标题路径，而不是从前缀反推——切片的 content 里本来就拼着标题路径前缀，理论上能 split 回来，但正文首行恰好长成那个形状就会误判。重新分块是纯函数、完全确定性，且**不重算 embedding**。每篇文档还会逐条比对本轮重算的 content 与库中 content，不一致就跳过整篇并告警——宁可不填，也不写错误的标题路径。

## 引用协议

### 元数据块

工具返回值形如：

```
⟦src[{"k":"3f9a2c1d4e5f","d":"<文档id>","b":"<知识库id>","c":22,
       "u":"<原文链接或null>","t":"标题","h":["架构设计","3.5 RAG 管道"]}, …]⟧
[kb:3f9a2c1d4e5f] [来源：架构设计]（关键词+语义）
片段正文…
```

- `k` 短 key（LLM 引用时抄这个）、`d` 文档 id、`b` 知识库 id、`c` 片段序号、`u` 原文链接、`t` 标题、`h` 标题路径
- 元数据块**固定在最前面**，且**所有返回路径都要输出**（含「未找到」「检索失败」，哪怕是个空数组）——这两条是安全前提，理由见下节
- 字段名刻意用单字母压缩：这块文本会永久留在 DB 里，且每个字段都要过一遍解析校验

### 展示编号是纯前端派生的

chip 上的 `[1]`、`[2]` **不由后端分配**，而是前端扫一遍回答正文，按「key 首次出现的顺序」现算。好处：

- 实时流与历史回放的输入完全相同（正文 + 工具结果）→ 算出的编号必然一致，不需要后端参与、也不需要持久化
- 检索到但**没被引用**的片段不占号，来源列表只列真正引用过的

### 短 key 的形式

`chunkId` 去掉连字符后取前 12 位十六进制。长度选择有个权衡：取 8 位（32 bit）在全库千级切片下生日碰撞概率约 0.05%，概率虽低但后果是「两条来源同 key → 白名单里后者被顶掉 → **静默错引到另一篇文档**」，加 4 个字符就能把这个风险压掉。

## 安全模型

元数据块是**信任锚**——它决定了 chip 能点向哪里；而它和被检索到的文档正文**同处一个字符串**。往知识库上传一份文档、正文里写一段伪造的 `⟦src[…]⟧`，就能污染白名单让用户点到攻击者指定的地址。这与 3.8 已堵的图片外链缺口是同一族问题，判据也一样：**凡文档/LLM 可控的字符串都不能当信任来源**。

四层防线：

1. **偏移 0 锚定** —— 工具固定写在最前面，前端解析用 `^` 锚定。伪造内容只能落在中后段，永远匹配不到。配套要求「任何返回路径都必须输出」，保证偏移 0 恒由工具自己写
2. **字段级校验** —— 文档 id / 知识库 id 必须匹配 UUID 格式（它们会被拼进请求路径）；原文链接必须 `https:` 且 host 恰为 `github.com`。任一字段非法就丢弃该条，宁可不显示也不让它决定跳转目标
3. **白名单** —— LLM 正文里写出的 key 必须在白名单里，才会被渲染成 chip；编造的 key 保持纯文本。未触发检索的对话白名单为空，一个 chip 都出不来
4. **外链防护** —— 打开外部链接时带 `noopener,noreferrer`，防被打开页面通过 `window.opener` 反过来改写本系统页面

补一条实现上的选择：**白名单过滤放在预处理阶段，不放在链接渲染规则里**。因为链接渲染规则的返回值必须与默认的闭合规则配对（后者恒定输出 `</a>`），在里面写降级分支会产出不配对的标签。职责切成两半——预处理只对白名单内的 key 生成链接，渲染规则只做纯改写、永远输出 `<a>`。

## 与规划的偏差

| 规划里写的 | 实际落地 |
|---|---|
| 自定义内部 scheme `kb://doc/{id}#chunk-{i}` 直接带上文档 id | 改成**编号 + 短 key**：内部链接只携带 12 位短 key，文档 id 等元数据另走元数据块。原因是让 LLM 抄 UUID 的可靠性太低 |
| 「需补 `chunks.heading_path` 结构化列」 | 用 jsonb 而非数组类型。原因是双驱动（本地 postgres-js / 生产 neon-http）对数组类型的返回形状未经验证，而「jsonb 经 `::text` 取出再 JSON.parse」这条路已由图片元数据列在生产验证过 |
| 「一次轻量回填」 | 回填确实是轻量的（不重算 embedding），但实现方式是**重新分块 + 逐条比对**，不是前缀反推 |
| 原文链接用分支还是 commit sha | 采用分支，与规划口径一致。已知退化：仓库后续提交后链接会漂移到新版本内容 |

## 验证

三层，从便宜到贵：

**① 检索层 A/B（发现了一个值得记的事实）**

改动只是往两条手写 SQL 的 SELECT 列表里加列，理论上不参与排序、不该影响召回。但评测跑出来 concept 是 10/12（83%），低于文档里记录的 92% 基线。把检索层单独还原到改动前再跑一次，结果**完全相同**——证明与本次改动无关，是**本地语料漂移**（语料已从 58 篇涨到 111 篇 / 2031 片），记录的 92% 基线在当前语料上已不可复现。

> 教训：**基线要连着语料状态一起看**。跨语料比对百分比会得出错误结论，只有同语料的 A/B 才是有效证据。

**② 渲染管线用真实模块做单元验证**

关键路径没法靠读代码确认，就用真实模块跑：伪造的元数据块被无视（锚定生效）、非 github.com 与明文 http 的链接被清洗成 null、非法文档 id 的条目被丢弃、代码块与行内代码里的标记不被误替换、渲染出的 chip 标签配对正确。

**③ 端到端**

真实发问 → 模型调用 5 次检索 → 白名单解析出 20 条来源 → 回答引用 5 个不同来源、**悬空 0 个**、渲染出 11 个 chip，且模型没有自己编「参考来源」列表、也没吐出元数据块。

## 踩坑

### 1. 短 key 取 12 位差点静默废掉整个功能（最值得记）

把 key 从 8 位改成 12 位后，单测立刻报「白名单为空」。原因：**UUID 的第 9 位是连字符**，直接 `slice(0, 12)` 会切出 `3f9a2c1d-4e5f` 这种带连字符的串，被「纯十六进制」的校验规则拒绝 → 元数据条目被整体丢弃 → 白名单恒空 → **所有引用静默降级成纯文本，且不报任何错**。

取 8 位时恰好停在连字符前，所以旧实现没暴露这个问题。

> 这类 bug 的危害在于「没有任何信号」：上线后只会表现为「引用功能时灵时不灵」，读代码基本看不出来。**能抓到它全靠拿真实模块跑了一遍。**

### 2. 链接渲染规则里不能写降级分支

实测：在 `link_open` 规则里返回 `<button>`，得到的是 `<button …>1</a>` 这种不配对标签；返回空串时还会漏出一个游离的 `</a>`。因为闭合规则的默认实现恒定输出 `</a>`，而它拿不到开标签上的属性。详见前文安全模型的最后一段。

### 3. 白名单按「轮」收窄 → 跨轮引用悬空

最初白名单只收「本轮 assistant 组的工具结果」。但 LLM 的引用可以跨轮：用户追问同一主题时，模型常常**不再检索、直接用上下文回答**，此时它会复用上一轮答案里的 `[kb:…]` → 查不到 → 悬空降级。用户看到的是「同一个来源，上一轮能点，这一轮变成一个奇怪的字符串」。

改用 chunkId 派生的 key 恰好让这个问题有了零成本的解法：key 跨轮天然不冲突、同一切片天然去重，所以白名单直接放宽到「整个对话」即可。

**顺带一个性能约定**：这份对话级白名单放在 store 层做一次计算，而不是每个消息气泡各算一份（否则 N 条消息就是 N 次全量重扫）。并且它**只读 `role:'tool'` 消息的内容**——不碰流式中的回答文本，否则每个 token 追加都会让它失效，退化成「每 token 重扫整个历史」。

### 4. 读取边界漏了两处元数据泄露

元数据只处理了「工具卡片的展示」，漏掉了两条直接读消息原文的旁路：

- **聊天列表的预览**：取最后一条消息的前 50 字符。当 Agent 检索完、最终回答还没开始生成时被中断（**切换对话会主动 abort**，所以相当常见），最后落库的正是 `tool` 消息 → 侧边栏直接显示 `⟦src[{"k":…` 的 JSON
- **跨对话搜索**：搜索匹配消息原文，结果列表又是直出 HTML → 搜到工具消息时同样露出

修法：在读取边界统一剥离（预览要**先剥再截断**，顺序反了没用）。历史消息接口保持不剥——前端正是靠它重建白名单。

## 关键洞察

- **元数据该放哪，取决于哪份数据是「实时与历史共用的唯一载体」** —— 找到那个载体，就不需要为两条路径各写一套，也不需要新增持久化
- **信任锚不能和不可信内容共处一个字符串** —— 一旦共处，「锚定偏移 0」就成了必须的防线，而不是可选优化
- **让失败可见**：引用标识用「查不到就降级」的短 key，而不是「写错一位也能命中」的序号。前者出问题用户看得见，后者会静默指向错误来源
- **前端派生优于后端分配**：展示编号不落库、不走协议，只要两侧输入一致就必然一致，少一个能出错的地方
- **基线要连着语料状态一起看**：跨语料比对召回率百分比会得出错误结论

## 已知限制

- **引用正确性无法保证**：白名单只保证「key 是本轮真实检索到的」，不保证模型把这段信息标对了来源。chip 能点 ≠ 引用正确
- **引用率不可控**：只人工验过一次，没有自动断言（现有评测脚本既不含知识库工具、也不看回答文本）
- **引用是快照**：覆盖上传会换文档 id；阶段 C 的 3.10 全量重灌后所有 id 换新 → **历史对话的引用会集体失效**
- **视觉观感尚未验收**：chip 样式、来源列表布局、预览弹层只在代码层面验证过
- **预览的图片白名单范围偏大**：预览整篇文档时按「该文档所有切片的图片并集」放行，从 GitHub 引入的第三方文档会一次性请求其全部图片
- 阶段 C 的下一步（3.10 Contextual Retrieval）尚未开始；线上库的建列与回填也待执行
