# 2026-08-17 — Prompt 评测-调优闭环：从设想到落地的实践与反思

> 调优的实质是「用真实输入测出行为 bug，再定点修」，不是「套业界模板」。评测脚本的价值是回归保护与量化，而非发现问题——当前规模下它是「休眠资产」。

---

## 讨论背景

承接 [7-09 提示词工程讨论](2026-07-09-prompt-engineering-and-phase2-planning.md) 第 2.4 节「评估集驱动迭代」的设想（当时只写了伪代码 `eval-cases.ts` + `run-eval.ts`，未落地）。本次真正实现了评测脚本，完成了第一轮真实调优，并在过程中产生了两点重要反思：**评测脚本在简单场景下是否「鸡肋」**，以及**「业界 prompt 规范」与「实测调优」到底是什么关系**。

## 核心内容

### 1. Prompt 分布盘点（5 层）

项目中的 prompt 分散在 5 个层级，没有集中管理：

| 层 | 位置 | 内容 |
|---|---|---|
| 用户自定义 system prompt | `prompt.store.ts` → `useChat.ts` → `schema.ts` | 用户自建，**无默认值**（不选就为空） |
| 后端拼接 system prompt | `api/chat/index.post.ts` | `dateContext`（当前时间）+ `toolUsageGuidelines`（工具调用准则） |
| system prompt 合并 | `utils/system-prompt.ts` | `extractSystemPrompt()` 合并显式 prompt 与 messages 里的 system |
| 工具描述 | `tools/builtin/*.ts` | 4 个工具的 `description` + 参数 `description` |
| 工具结果包装 | 各工具 `execute()` + `runner.ts` 错误文案 | 喂回 LLM 的 `role: 'tool'` 内容 |

**两个关键事实**：
- `factory.ts` 永远返回 `OpenAIProvider`（OpenAI 兼容格式），`DeepSeekProvider` 是废弃学习代码，未被引用。
- 工具在 `tools/index.ts` **无条件注册 4 个**，所以 `toolDefinitions.length > 0` 恒成立 → 所有请求都走 Agent 路径，纯聊天 else 分支实际走不到。

### 2. 工具 description 审计（6 条问题）

| # | 问题 | 风险 | 最终处理 |
|---|---|:---:|---|
| #1 | web_search / web_fetch 边界模糊 | 高 | 两个 description 加互斥边界 |
| #2 | toolUsageGuidelines 缺「场景→工具名」映射 + 过度保守 | 中高 | **改 system prompt（唯一实测确认的真问题）** |
| #3 | web_search 描述「关键词」vs 参数「自然语言问题」矛盾 | 中 | 统一为「搜索查询」 |
| #4 | current_time 默认时区重复描述 | 低 | 删 description 里的重复句 |
| #5 | calculator 描述漏科学计数法 `eE` | 低 | 补「如 1e10」 |
| #6 | deepseek.ts 死代码 + supportsTools 不一致 | — | 顶部加「已废弃」标注（保留学习代码未删） |

### 3. 评测脚本实现（scripts/eval-prompt/）

采用**快照版（方式 A）**而非抽取公共函数（方式 B），理由：要「最快拿到基线数据」且**不碰线上代码**。代价是快照会漂移（见关键洞察 4）。

- `cases.mjs`：10 个 case，声明「期望工具 + 期望参数」，覆盖负例（闲聊不调工具）+ 4 个工具 + 模糊 case
- `run.mjs`：快照 system prompt + 工具定义 → fetch OpenAI 兼容接口（`stream: false`）→ 规则判定（工具名对不对 + 参数对不对）
- 跑法：`node --env-file=.env scripts/eval-prompt/run.mjs`
- 判定维度**只有**「工具选择 + 参数」，不评测答案质量、多工具协作、拒绝场景

### 4. 调优闭环实战（80% → 100%）

- **基线**：8/10。失败 `calc-b`（100/3 被心算，属 case 期望偏严）+ `ambiguous`（「查一下 Vue ref」被当常识直接答）
- **根因**：`toolUsageGuidelines` 那句「不确定就不要调用」**太保守**，导致边缘场景一律不调工具
- **修复**：加「场景→工具名」显式映射 + 「用户明确要求查询/查一下/最新就应搜索，不要凭记忆回答」
- **结果**：10/10，且负例（你好/冷笑话）未崩——证明修好漏调的同时没引发乱调
- 之后清理 #1 #3 #4 #5 #6，重跑仍 10/10，无回归

### 5. 反思：评测脚本的「鸡肋」本质

走完闭环后，得出一个诚实的结论：**当前阶段这套评测确实鸡肋**，三个原因：

1. **评测维度太窄**——只统计「工具选没选对」，本质是个「工具调用正确率计数器」，配不上「调优」这么重的词
2. **prompt 不复杂**——system prompt 就两段、工具就 4 个、description 就一句话，人工问几句就能覆盖
3. **频率太低**——跑一次发现 bug、改完就闲置，不是持续资产

真正的收获不是脚本本身，而是**判断力**：能判断「什么时候需要评测、什么时候不需要」。脚本定位为「休眠资产」——不删（重建要重写）、不跑（不跑不花钱）、不维护，触发条件是「工具数涨到 6~10 个、prompt 开始加约束/few-shot、或改 A 坏 B 真的发生」。

### 6. 反思：业界规范 vs 实测调优

最初以为「调优 = 套业界规范（CO-STAR/CRISPE/ICIO）改 prompt」，实测后发现有偏差：

| | 规范（框架） | 实测（评测） |
|---|---|---|
| 解决什么 | 从零写 prompt 时怎么写**完整** | 写完后怎么知道它**对** |
| 手段 | 静态 checklist（要素全不全） | 动态测试（行为对不对） |
| 时机 | 写之前/写的时候 | 写之后/改的时候 |
| 类比 | 代码规范、最佳实践 | 单元测试 |

**规范是「防遗漏」，实测是「纠错」**，作用于不同阶段、不可互相替代。本次全程走的是实测纠错——问题（漏调）是藏在「不确定就不调」这句**看起来合理**的规则里的行为 bug，静态看文案永远看不出来，规范对它无能为力。规范的边际价值在 prompt **复杂到一眼看不过来**时才显现（多段约束/输出格式/few-shot/多工具）。

## 关键洞察

- **调优的实质是「用真实输入测出行为 bug，再定点修」，不是「套业界模板」**。行为 bug 只能实测暴露，静态审计只能列出「假设」，且会虚报（本次审计 6 条，实测只确认 1 条真触发）
- **规范与实测是两回事**：规范防遗漏（写作指南）、实测纠错（测试修复）。简单 prompt 下规范边际价值趋近零，但复杂 prompt 下它是唯一防「漏写关键约束」的手段
- **评测脚本的价值是「回归保护 + 量化」，不是「发现问题」**。发现问题靠 agent 静态分析，脚本只能测你写进去的 case
- **快照漂移是评测脚本最大的维护陷阱**：线上 prompt 与评测快照是两份，改一处必须同步另一处，否则评测测的是假数据（约定已写进 `run.mjs` 顶部注释）
- **真正的收获是判断力**：能判断「什么时候需要评测、什么时候不需要」，这比脚本本身更值钱
