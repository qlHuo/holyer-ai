# 2026-08-31 — ReAct 轮数限制 vs 工具调用预算：Agent 资源管理的边界

> 核心洞察：轮数限制管不住"一轮发一堆调用"——真正给 Cloudflare 资源封顶的是「工具调用总次数预算」，不是迭代轮数。CPU 不是轮数的约束，I/O 等待才是。

---

## 讨论背景

Agentic RAG 实测时发现：问「说明项目整体流程」触发了 **15 个工具调用**（5 轮 × 每轮 3 个），逼近 Cloudflare Workers 免费版的子请求/CPU 配额。此前为兼容 CF 把轮数从 10 改到 3，本地实测 3 轮常提示"达到最大调用次数"又改回 10——**来回调轮数都没解决根本问题**。

## 核心认知

### 1. CPU 不是轮数限制的真正约束

每轮 ReAct 绝大部分时间在"等 LLM API + 等 DB"（I/O 密集），Worker 等待时是空闲的，不吃 CPU。Cloudflare 的 CPU 限制卡的是"计算量"（JSON 解析、格式化），不是"等待时间"。所以"为 CPU 砍轮数"的理由本身不成立——10 轮的 CPU 消耗可能只有几十毫秒。

### 2. 轮数限制的真实作用

轮数限制（`maxIterations`）其实是：① 防 LLM 无限循环；② 控总延迟和 token 成本。跟资源配额关系不大。

### 3. 真正要封顶的是「工具调用总次数」

每个工具调用 ≈ 2 次 HTTP 子请求（如 `search_knowledge_base` = 1 embedding + 1 DB 查询）。15 个调用 ≈ 30+ 子请求，这才是逼近 CF 免费版红线的地方。所以资源封顶的正确手段是 **`maxToolCalls`**（工具调用总次数预算），不是 `maxIterations`。

## 方案：maxToolCalls 预算 + 优雅降级

在 runner 加 `maxToolCalls`（默认 8），累计工具调用数，超过即终止。关键是**优雅降级而不是甩错误**：

```
预算内：LLM 带 tools → 正常检索
预算耗尽：下一轮 LLM 调用【不带 tools】→ 只能输出文本 → 走最终回答流式路径
```

- **截断**：一轮里 LLM 想调 5 个但只剩 2 个额度 → 只执行前 2 个，memory 也只记录这 2 个（避免孤儿 tool_call 破坏配对不变量）
- **不带 tools 强制回答**：预算耗尽后注入提示「基于已收集的信息直接回答」，LLM 无法再调工具，只能收尾——用户体验顺畅，不甩"达到上限"错误

## 补充：两个上限的数学关系与一致性

### 有效轮数 ≤ maxToolCalls + 1

每个非最终轮至少产生 1 个工具调用（0 个 = 纯文本 = 最终回答 = 循环立即结束），因此：

> **有效轮数 ≤ maxToolCalls + 1**（+1 是最后的回答轮，不调工具）

默认 `maxToolCalls = 8` 时：1 工具/轮 → 最多 9 轮；3 工具/轮（并发）→ 最多 4 轮。所以 `maxIterations = 10` 正常流程下**基本触达不到**——它是"循环兜底"（防死循环的保险丝），不是"资源预算"。二者是分层关系：正常流程用工具预算收尾，异常流程才靠轮数兜底。

### maxIterations 触达也改成优雅降级

早期"达到迭代轮数 → 甩错误"与工具预算的优雅降级不一致（且默认下是死代码）。已统一：达到轮数上限时同样注入提示 + 空 tools 强制最终回答——无论哪个上限先触发，用户体验一致（有答案、不中断）。

## 关键洞察

- **轮数 ≠ 资源**：把"轮数限制"当"资源限制"是概念混淆。轮数管循环次数，工具调用数才管资源（子请求/CPU）
- **并发是把双刃剑**：引导 LLM 并行检索能压缩轮数，但引导过头会变成"每轮都并行搜、还搜多轮"的过度检索——需要预算兜底
- **硬约束 + 软引导**：预算（硬，封顶资源）+ 工具描述引导（软，收敛 LLM 行为）配合，缺一不可
